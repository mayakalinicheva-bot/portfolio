# 1. Q71. Платформы для просмотра и публикации работ

Респонденты используют разные внешние сервисы.

В независимой выборке упоминаются:

- Pinterest;

- Behance;

- Dprofile;

- социальные сети;

- различные зарубежные portfolio-платформы;

- Google Docs как способ демонстрации отдельных материалов.

SELF01 дополнительно использует:

- Instagram;

- TikTok;

- Behance;

- Pinterest.

Единого сервиса, который полностью закрывает все задачи респондентов, не выявлено.

Разные сервисы используются для разных целей.

### Pinterest

Преимущественно:

- вдохновение;

- насмотренность;

- поиск референсов;

- поиск отдельных визуальных решений.

### Behance / Dprofile

Преимущественно:

- просмотр оформленных кейсов;

- профессиональная самопрезентация;

- публикация собственных работ;

- поиск референсов.

### Социальные сети

Преимущественно:

- discovery авторов;

- просмотр работ;

- профессиональный контент;

- процесс создания работы;

- образовательный контент.

Следовательно, проблема Portfolio не заключается в полном отсутствии внешних платформ для просмотра творческих и профессиональных работ.

---

# 2. RF-71. Portfolio не должен заменять Behance или Pinterest

> **Студенты используют несколько внешних платформ для просмотра и публикации творческих работ, причём разные сервисы закрывают разные задачи. Portfolio не должен заменять универсальные профессиональные и inspiration-платформы; его отдельная ценность заключается в систематизации публикации и discovery работ внутри сообщества IThub.**

Portfolio не позиционируется как:

- новый Pinterest;

- полный аналог Behance;

- замена Dprofile;

- универсальная профессиональная социальная сеть для всего рынка.

Его отдельная ценность:

**единое пространство работ конкретного образовательного сообщества IThub.**

---

# 3. Q72–Q73. Подписки на профессиональных авторов

Респонденты следят за разными типами авторов:

- дизайнерами;

- креативными агентствами;

- дизайн-студиями;

- преподавателями;

- профессиональными специалистами;

- авторами образовательного контента;

- другими студентами.

Причины подписки:

- стиль;

- качество работ;

- идеи;

- авторский почерк;

- профессиональная релевантность;

- интересные решения;

- насмотренность;

- полезность контента.

Особенно значим ответ R07: респондент подписывается в том числе на **других студентов с сильным уровнем и интересными идеями**.

Следовательно, интерес к другому студенту как автору уже существует независимо от концепции Portfolio.

---

# 4. RF-72. Работа может становиться точкой входа в автора

> **Интерес к автору формируется прежде всего через его работы, стиль, идеи, компетенции и профессиональную релевантность, а не только через известность. В выборке присутствует реальный опыт подписки на других студентов из-за уровня их работ, что поддерживает существующую механику подписки на авторов внутри Portfolio.**

Потенциальный flow:

**пользователь видит работу**

→ **работа вызывает интерес**

→ **переходит в профиль автора**

→ **просматривает другие проекты**

→ **подписывается на автора**

→ **получает возможность обнаруживать его последующие публикации.**

Следовательно, существующая механика **subscriptions/following** сохраняется.

Новой сущности для этого не требуется.

---

# 5. RF-73. Насмотренность как самостоятельная ценность discovery

Несколько независимых респондентов прямо используют чужие работы для:

- развития насмотренности;

- поиска референсов;

- анализа визуальных решений;

- поиска идей;

- понимания способов оформления;

- поиска ориентиров;

- вдохновения.

Таким образом, просмотр чужих проектов не является только развлечением или способом найти конкретного автора.

> **Просмотр чужих проектов выполняет для части студентов образовательную и профессионально-развивающую функцию: работы используются для насмотренности, поиска референсов, анализа решений и вдохновения. Следовательно, discovery внутри Portfolio имеет самостоятельную ценность и не является только вспомогательным способом найти конкретного автора.**

Это дополнительно поддерживает:

- recommendation feed;

- направления;

- фильтрацию;

- bookmarks;

- профили авторов;

- public discovery.

# 6. Одна база проектов — несколько пользовательских задач

Совокупный анализ интервью показывает, что одна и та же сущность Work/Case может иметь различную ценность для разных аудиторий.

### Для студента

- насмотренность;

- inspiration;

- reference discovery;

- feedback;

- professional self-presentation;

- networking.

### Для абитуриента

- понимание направления;

- сравнение специальностей;

- просмотр реальных результатов обучения.

### Для преподавателя

- discovery сильных работ;

- feedback;

- Teacher Award;

- профессиональные примеры.

### Для потенциальной профессиональной аудитории

- знакомство с навыками;

- просмотр кейсов;

- понимание процесса и вклада автора.

Следовательно, Work/Case остаётся центральной сущностью продукта.

---

# 7. Q74–Q75. Like и Save не являются одним действием

Интенсивность использования социальных реакций различается.

Часть респондентов активно ставит likes и сохраняет работы.

Часть делает это редко.

Некоторые практически не используют эти действия.

Следовательно, нельзя утверждать, что likes и saves одинаково важны каждому студенту.

Однако среди пользователей Save наблюдается устойчивое назначение.

Работы сохраняют:

- как референсы;

- ради отдельных визуальных решений;

- ради идей;

- ради интересной подачи кейса;

- чтобы вернуться позднее;

- ради полезной информации;

- ради профессионально релевантного решения.

---

# 8. RF-74. Like ≠ Save

> **Like и Save выполняют разные задачи. Like является преимущественно лёгкой социальной реакцией, тогда как Save используется частью студентов как личный инструмент накопления референсов, полезных решений и проектов для последующего возвращения. Это поддерживает существующее разделение likes и bookmarks/saves в Portfolio.**

Следовательно:

**Like** = социальная реакция.

**Save / Bookmark** = личное сохранение для последующего использования.

Эти действия не следует объединять в одну механику.

---

# 9. Связь Save с recommendation algorithm

Ранее для персонального behavioral signal была принята относительная система:

- open = 1;

- like = 2;

- comment = 3;

- save = 4.

Q74–Q75 не определяет точные математические коэффициенты.

Однако качественные данные поддерживают сам принцип:

> **Save может являться более сильным сигналом личного интереса, чем Like.**

Like может обозначать простую положительную реакцию.

Save чаще означает:

> «Эта работа достаточно релевантна или полезна мне, чтобы я хотел вернуться к ней позднее».

Следовательно, существующий относительный порядок behavioral signals получает дополнительное qualitative evidence.

Точные коэффициенты остаются алгоритмическим решением.

---

# 10. Q76. Публичный комментарий имеет высокий interaction cost

В независимой выборке публичные комментарии встречаются значительно реже, чем просмотр, likes или saves.

Несколько респондентов:

- никогда публично не комментируют;

- практически не комментируют;

- предпочитают обсуждать работу лично;

- дают feedback в переписке;

- обсуждают проекты со знакомыми.

SELF01 также указывает, что публичный комментарий требует значительно большего усилия, поскольку:

- его увидит автор;

- его могут увидеть другие пользователи;

- необходимо сформулировать собственную позицию;

- возникает большая социальная ответственность за написанное.

Таким образом, comment является более дорогим пользовательским действием.

---

# 11. RF-75. Отсутствие комментария ≠ отсутствие интереса

> **Публичный комментарий имеет значительно более высокий interaction cost, чем Like или Save. Многие респонденты обсуждают работы лично или в переписках, но почти никогда не оставляют публичные комментарии. Поэтому низкое количество комментариев не следует автоматически интерпретировать как отсутствие интереса к работе или потребности в feedback.**

Это важно учитывать при будущей продуктовой аналитике.

Например:

**много просмотров + saves + likes + мало comments**

не должно автоматически интерпретироваться как низкая ценность публикации.

---

# 12. Не создавать искусственные feedback-механики без дополнительного evidence

Q76 показывает барьер публичного комментирования, но не показывает конкретного решения этого барьера.

Поэтому на основании блока не добавляются:

- шаблоны комментариев;

- anonymous feedback;

- обязательные оценки;

- feedback forms;

- reaction presets;

- peer review system.

Существующая механика Comments сохраняется.

После запуска её реальное использование должно оцениваться через продуктовую аналитику.

---

# 13. Q77. Содержательный публичный feedback практически отсутствует

Ни один независимый респондент не сообщает об устойчивом опыте получения содержательной обратной связи на опубликованные работы в интернете.

Ответы преимущественно:

- «нет»;

- «не получал»;

- «не помню».

R07 отдельно отмечает feedback преподавателей.

SELF01 также не получает содержательных комментариев на Behance, но регулярно получает feedback:

- от друзей;

- одногруппников;

- знакомых;

- преподавателей.

Следовательно, полезная обратная связь существует, однако преимущественно находится **вне публичного слоя профессиональных платформ**.

---

# 14. RF-76. Meaningful public feedback gap

> **Содержательная публичная обратная связь на опубликованные работы практически отсутствует в опыте независимых респондентов. Полезный feedback чаще возникает в личном общении или от преподавателей. Portfolio потенциально может сделать такую обратную связь более доступной внутри профессионально связанного сообщества, но её фактическое возникновение после запуска требует проверки.**

Важно:

Portfolio **не гарантирует**, что пользователи начнут активно давать качественный feedback.

Это opportunity, а не доказанный outcome.

---

# 15. Связь feedback с Teacher role

Респонденты неоднократно связывают полезную обратную связь с:

- преподавателями;

- специалистами;

- более опытными людьми;

- профессионалами из соответствующей области.

Это дополнительно поддерживает существующую роль Teacher.

При этом блок **не создаёт основания возвращать отдельную mentoring system**.

Для текущей модели достаточно:

- Comments;

- Teacher identity;

- Teacher Award;

- существующего Expert signal.

Teacher может дать feedback, но не получает контроль над чужой публикацией.

---

# 16. Q78. От чего зависит доверие к feedback

В ответах повторяются два основных фактора.

## 1. Source credibility

Пользователь оценивает:

- профессиональный опыт;

- компетентность;

- специальность;

- сферу деятельности;

- авторитетность;

- собственное знание человека.

## 2. Feedback quality

Пользователь оценивает:

- аргументированность;

- конструктивность;

- подробность;

- объяснение причины;

- возможность понять, как улучшить решение.

Следовательно, комментарии субъективно не воспринимаются как равнозначные.

---

# 17. RF-77. Компетентность источника влияет на ценность feedback

> **Доверие к обратной связи определяется сочетанием компетентности её автора и качества аргументации. Комментарии разных пользователей не воспринимаются как равнозначные по профессиональной ценности.**

Это дополнительно поддерживает:

- отображение роли Teacher;

- Teacher Award;

- Expert signal.

Но не обосновывает:

- reputation score;

- рейтинг пользователей;

- expert points;

- автоматическую оценку качества комментариев;

- сложную reputation system.

---

# 18. Teacher Comment и Teacher Award — разные сигналы

Важно сохранить различие.

### Teacher Comment

Содержательное мнение или рекомендация преподавателя.

### Teacher Award

Экспертное выделение конкретной работы.

Они могут сосуществовать, но не являются одной механикой.

Ни одна из них не даёт преподавателю:

- edit;

- delete;

- publish;

- archive;

- visibility control

над чужим кейсом.

---

# 19. Q79. Реакции влияют на автора

Большинство независимых респондентов указывают хотя бы частичное влияние:

- просмотров;

- likes;

- других реакций.

Степень влияния различается.

Для некоторых это влияет на отношение к работе.

Для других — скорее на мотивацию.

Некоторые сознательно отделяют собственную оценку качества от внешней популярности.

Следовательно, социальные показатели имеют значение, но не являются объективной профессиональной оценкой.

---

# 20. RF-78. Engagement ≠ Quality

> **Количество просмотров и реакций способно влиять на восприятие собственной работы и особенно на мотивацию автора, однако социальная популярность не должна интерпретироваться продуктом как объективный показатель качества проекта.**

Следовательно:

**много likes ≠ автоматически качественная работа.**

**мало likes ≠ автоматически слабая работа.**

Это дополнительно поддерживает существующую recommendation architecture:

**Relevance + Engagement + Freshness + Expert**

вместо:

**likes = ranking.**

Engagement является одним из сигналов, но не единственным определением качества или позиции работы.

---

# 21. Q80. Feedback способен влиять на дальнейшую работу

Большинство независимых респондентов имеют опыт, когда feedback:

- учитывался;

- приводил к изменениям;

- помогал улучшить проект;

- влиял на дальнейшие решения.

Особенно значим feedback:

- преподавателей;

- профессионалов;

- более компетентных знакомых;

- сильных студентов.

При этом R03 демонстрирует более автономную позицию: внешняя оценка не обязательно заставляет менять работу, если сам автор уверен в результате.

Это важное исключение.

---

# 22. RF-79. Feedback → Iteration, но контроль остаётся у автора

> **Обратная связь может влиять на дальнейшие решения и доработку проекта. Для большинства независимых респондентов существует опыт учёта замечаний других людей, особенно если источник воспринимается как компетентный. При этом окончательное решение остаётся за автором.**

Это полностью соответствует ранее принятому принципу author autonomy.

Feedback является:

**советом / профессиональным сигналом / мнением.**

Feedback не является:

**правом управления чужой работой.**

---

# 23. Permission model подтверждается ещё раз

Для чужого публичного кейса зарегистрированный пользователь потенциально может:

- просматривать;

- ставить Like;

- сохранять;

- комментировать;

- подписываться на автора.

Teacher дополнительно может в рамках существующих правил:

- оставить comment;

- назначить Teacher Award.

Но эти действия не дают права:

- редактировать чужой кейс;

- удалять его;

- изменять visibility;

- публиковать вместо автора;

- архивировать вместо автора.

---

# 24. Views получают отдельное подтверждение

Q79 напрямую исследует влияние:

- просмотров;

- реакций.

Q111–Q120 также показал:

- просмотры;

- внимание;

- реакции;

- recognition

как предполагаемые причины возвращения на платформу.

Следовательно, Views больше не рассматриваются как случайная второстепенная метрика.

Количество просмотров является значимым социальным сигналом для автора и может выполнять мотивационную функцию.

---

# 25. RF-80. Views как базовая статистика кейса

> **Количество просмотров опубликованного кейса должно отображаться как базовая социальная статистика работы. Просмотры показывают автору и допустимой аудитории факт внимания к публикации, но не должны интерпретироваться как объективная оценка качества проекта.**

Это не требует полноценной analytics dashboard.

На базовом уровне кейс может иметь:

- Views;

- Likes;

- Saves;

- Comments.

Расширенная аналитика остаётся отдельным вопросом MVP/Post-MVP.

---

# 26. Главное правило видимости Views

Принято базовое правило:

> **Видимость счётчика просмотров не может быть шире текущей видимости самого кейса.**

Иными словами:

**кто имеет право видеть кейс, тот может видеть и его публичную статистику просмотров в рамках соответствующего режима доступа.**

---

# 27. Public case

Если кейс имеет статус публичного:

- его может просматривать публичная аудитория;

- количество просмотров видно всем пользователям, которые видят кейс;

- для просмотра самого кейса авторизация не требуется;

- счётчик Views является частью публичной статистики работы.

Модель:

**Public Case → Public Views Counter.**

Это соответствует Guest browsing.

---

# 28. Author-only case

Если кейс доступен только автору:

- внешние пользователи не могут открыть кейс;

- внешние просмотры не начисляются;

- собственные открытия автора не увеличивают Views;

- до изменения visibility внешняя статистика просмотров фактически отсутствует.

Модель:

**Author-only Case → 0 external views.**

Если автор позднее переводит кейс в Public, с этого момента начинается накопление внешних просмотров.

---

# 29. Friends-only case

Если кейс доступен только друзьям:

- открыть его могут только пользователи, входящие в разрешённую аудиторию;

- Views видны этой же аудитории;

- пользователи вне разрешённой аудитории не видят ни кейс, ни его статистику;

- собственные открытия автора не должны увеличивать внешний счётчик.

Модель:

**Friends-only Case → Friends-only Views Counter.**

То есть:

> **видимость статистики наследует visibility кейса.**

---

# 30. Изменение visibility

Необходимо различать:

**право видеть статистику**

и

**историю уже накопленной статистики.**

Базовое решение:

### Author-only → Public

После публикации начинаются внешние просмотры.

### Author-only → Friends-only

После предоставления доступа разрешённой аудитории начинаются внешние просмотры.

### Public → Friends-only

Кейс перестаёт быть публично доступным.

Счётчик больше не показывается внешней публичной аудитории и наследует новый friends-only access.

### Friends-only → Public

Кейс и счётчик становятся доступны публичной аудитории.

Таким образом, изменение visibility меняет **круг пользователей, имеющих доступ к статистике**, вместе с доступом к самому кейсу.

---

# 31. Что пока НЕ определяется

Текущим решением не требуется окончательно фиксировать:

- считаются ли только unique views;

- какое временное окно используется для повторного просмотра;

- учитываются ли просмотры неавторизованных Guests;

- защита от bot traffic;

- защита от искусственного накручивания;

- техническая дедупликация;

- real-time или delayed counter;

- место отображения Views на карточке;

- подробная статистика по времени;

- источники переходов;

- viewer identities.

Это engineering/analytics layer, который должен прорабатываться отдельно.

---

# 32. Privacy guardrail

Базовый Views Counter показывает **количество просмотров**, а не обязательно личности просмотревших.

Решение:

> **«1 248 просмотров»**

не означает автоматически:

> **«показать автору список всех 1 248 пользователей».**

Viewer identity является отдельным privacy/product вопросом и не выводится из текущих интервью.

---

# 33. Связь Views с recommendation algorithm

Views являются социальной статистикой, но это не означает, что raw view count должен напрямую повышать ranking.

Иначе возникает риск:

**больше показов → больше views → ещё выше ranking → ещё больше показов.**

Это способно создавать self-reinforcing popularity loop.

Следовательно:

> **Views Counter и ranking signal — разные продуктовые вопросы.**

Отображение Views пользователю подтверждено.

Использование raw Views в recommendation score этим решением **не утверждается**.

# 34. Итоговые Research Findings Q71–Q80

## RF-71

Студенты используют разные внешние сервисы для просмотра и публикации работ. Portfolio не должен заменять универсальные профессиональные и inspiration-платформы; его отдельная ценность заключается в IThub-specific publishing и discovery.

## RF-72

Интерес к автору может формироваться через качество, стиль, идеи и профессиональную релевантность его работ. Реальный опыт подписки на сильных студентов поддерживает существующую механику subscriptions.

## RF-73

Просмотр чужих проектов имеет самостоятельную образовательную и профессиональную ценность через насмотренность, inspiration, references и анализ решений.

## RF-74

Like и Save имеют разную семантику. Like является лёгкой социальной реакцией, Save — инструментом сохранения релевантных материалов для последующего возвращения.

## RF-75

Public Comment имеет более высокий interaction cost, чем Like или Save. Малое количество комментариев не должно автоматически интерпретироваться как отсутствие интереса.

## RF-76

Содержательный публичный feedback практически отсутствует в опыте независимой выборки. Полезная обратная связь чаще возникает лично или от преподавателей. Portfolio имеет opportunity улучшить доступность feedback, но результат требует проверки после запуска.

## RF-77

Ценность feedback зависит от компетентности автора и качества аргументации. Это поддерживает Teacher identity и Expert signal, но не требует отдельной reputation system.

## RF-78

Views и реакции способны влиять на мотивацию и восприятие собственной работы, но social engagement не является объективной оценкой профессионального качества.

## RF-79

Feedback способен влиять на дальнейшие решения и итерации проекта, однако окончательный контроль над работой остаётся у автора.

## RF-80

Views становятся базовой статистикой кейса. Видимость Views наследует visibility работы: публичный кейс имеет публичный счётчик, friends-only кейс показывает статистику только разрешённой аудитории, а author-only кейс не получает внешних просмотров до расширения доступа.

# 35. Влияние блока на Requirements Matrix

## Подтверждаются существующие требования

- Like;

- Save / Bookmark;

- Comments;

- Subscriptions;

- Notifications;

- Recommendation Feed;

- Public Discovery;

- Teacher identity;

- Teacher Award;

- Expert signal;

- Author autonomy;

- Case visibility.

## Уточняется существующая recommendation logic

Engagement остаётся одним из ranking signals, но не должен автоматически приравниваться к качеству.

Save получает дополнительное qualitative justification как более сильный personal-interest signal по сравнению с Like.

## Добавляется / уточняется Views

**Case Views Counter**

Базовые правила:

1. кейс имеет счётчик внешних просмотров;

2. собственные открытия автора не увеличивают внешний счётчик;

3. Public → Views видны всем, кто видит кейс;

4. Friends-only → Views видны только разрешённой аудитории;

5. Author-only → внешние Views не начисляются;

6. при расширении visibility начинается возможность получения новых внешних просмотров;

7. видимость статистики наследует текущую visibility кейса;

8. Views не являются автоматической оценкой качества;

9. отображение Views не означает раскрытие viewer identities;

10. использование Views внутри recommendation ranking требует отдельного решения.
